# ADR-055: Sentry captureFeedback как канал пользовательского фидбека

- Статус: Принято
- Дата: 2026-09-14
- Контекст: issue #414 «Форма обратной связи и ошибок» (план согласован
  code-quality-reviewer, зафиксирован в issue)

## Контекст

Issue #414 исходно ставил задачу «организация формы багов через GitHub
issues». В ходе обсуждения требование пересмотрено:

- **GitHub-путь отвергнут**: юзеру нужен аккаунт GitHub, переход на внешний
  ресурс, самостоятельное заполнение контекста. Для RU-аудитории добавляется
  ещё и нестабильный доступ к github.com.
- Технические ошибки (краши, сбои сети) уже идут в Sentry автоматически
  (ADR-036) — после закрытия дыр логирования (первый срез плана) ручной
  репорт для них не нужен.
- Реальная дыра — «человеческие» проблемы, которые Sentry не видит: неверный
  контент (перевод токена, данные карточки) и кривое распознавание (OCR/STT
  выдали мусор без ошибки).

## Решение

Канал доставки репортов — **Sentry user feedback API** (`captureFeedback`),
вызываемый из уже интегрированного JS SDK (ADR-036):

- Свой UI: модалка `FeedbackModal` в стиле дизайн-системы, отправка через
  `captureFeedback({message}, {captureContext: {tags, extra}})`.
- Теги `feedback_category` / `feedback_source` / `app_version` / `platform` /
  `page` / `ui_language` — триаж в feedback stream фильтрами.
- Транспорт отвязан от UI трейтом `FeedbackSink` (+ стёртая `FeedbackSubmitFn`
  в контексте): переезд на альтернативу (например, таблицу TrailBase) не
  потребует менять UI.
- Точки входа живут в моменте фрустрации и сами собирают «предмет» репорта:
  попап перевода токена («Неверный перевод?») и кнопка ⚠ в шапке урока
  (активна после показа ответа — предмет собирается из раскрытого ответа,
  иначе модалка спойлерила бы ответ; disabled на фазе вопроса стабилизирует
  layout шапки).

## Оговорки и компромиссы

- **Retention 30–90 дней** (free tier) — репорты не образуют backlog; принят
  быстрый цикл «увидел → поправил контент → закрыл».
- **Анонимность**: имя/email не собираются; анти-спам — клиентский cooldown
  15 с после успешной отправки + лимит 2000 символов; квоты Sentry
  наблюдаются после релиза.
- **Feedback stream ≠ Issues**: нет fingerprint-группировки; триаж через теги.
  Фильтруемость тегов проверяется на staging до релиза.
- **Дрейф мажорных версий лоадера** (прецедент v7→v8, см. `sentry.rs`):
  `captureFeedback` — API v8+; код защитён на отсутствие метода.
- **Пустой compile-time DSN** (dev/e2e-сборки) — единственный легитимный
  триггер информационного состояния «Отправка доступна в релизных сборках».
  Runtime-недоступность при настроенном DSN — error-ветка с повтором:
  релизный юзер не должен видеть «только в релизных сборках» внутри релиза.
- Точки входа рендерятся всегда (e2e-сборка без DSN видит форму и ассертит
  info-состояние; `.github/workflows/` не трогаем).

## Последствия

- Пользователь сообщает о проблеме in-app, без GitHub, в момент фрустрации,
  с автоматически приложенным контекстом (версия, платформа, страница, язык,
  предмет репорта).
- Мейнтейнер триажирует репорты в Sentry по тегам категорий.
- Запасной путь (TrailBase-таблица) остаётся за абстракцией `FeedbackSink`.

## Не делается (scope)

GitHub Issue Forms; Sentry event id / install_id в репорте; скриншоты
(срез 2+, после проверки attachments в WebView); общий вход через Profile;
кнопки в Alert-компонентах (дубль автоматического Sentry); вход в фазе
вопроса карточки (спойлер ответа); авто-перенос фидбека в GitHub issues.

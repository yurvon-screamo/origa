# A/B-отчёт: 6 моделей JA→{en,vi,ru,ko} на 40k мультилокальном сете

**Дата:** 2026-09-25 · **Данные:** 156 228 JP-предложений с очищенными переводами (аудит марафона:
16 710 фиксов + 599 гугл-вердиктов), QLoRA 4-bit NF4 + LoRA r=16 α=32 all-linear, bs 8 × accum 4,
LR 2e-4 cosine (warmup 3%), 1 эпоха, Intel Arc B390 (XPU).

**Eval:** holdout 500×4 (в обучении не участвовал), 100 фраз/локаль, greedy, chrF (sacrebleu).
chrF — символьное пересечение с эталоном: 0 ≈ не на том языке/мимо, 30+ ≈ близко к содержанию.
Метрика занижает честные перефразы — относительное сравнение моделей корректно.

## Ключевые выводы

1. **Мультиязычность решает база, не SFT.** LFM-малыши (230/350M) не держат локаль:
   RU-ответы — короткие мимо-фразы или не-русский (ES/JP/EN-примеси), KO — 0 хангыля.
   Qwen (обе версии) генерят чистый хангыль уже на 2k.
2. **Инверсия карты моделей:** RU не заявлен у LFM2.5, но 1.2B даёт 32.5; KO заявлен,
   но LFM даёт ~1. Список языков в карте ≠ прейтрейн-масса: русского веб-текста много,
   SFT направляет; KO-сигнала в базе LFM нет — активировать нечего.
3. **Токенайзер — множитель сложности.** LFM 64k словарь, 0 хангыль/кириллических токенов,
   byte-fallback: KO 0.74 tok/char, VI 0.80 против EN 0.22. Дорогие локали = слабые chrF
   на равных данных. У Qwen словарь шире: RU 0.31, VI 0.30.
4. **Масштаб LFM**: 1.2B >> 350M > 230M по всем локалям; но даже 1.2B не вытягивает KO.
5. **Кривая данных Qwen3-0.6B**: 2k→10k даёт +2.3 avg (не насытилась).

## Инфраструктура (грабли → фиксы)

- Unified/device memory: OOM-киллер бил шелл → cgroup-клетка `systemd-run MemoryMax`
- Qwen3.5: 248k словарь → логиты 2-4GB в loss → тихий SIGKILL → **masked CE** (logits только
  на обучающих позициях) — решено
- Ризонинг Qwen: `enable_thinking=False` — у Qwen3 opt-in, у Qwen3.5 default-off (jinja карт)
- total_steps считался от константы EPOCHS вместо a.epochs (LR-косинус растянут вдвое)
- Скобочные паттерны в pkill; `&` биндит всю `&&`-цепочку (cd уезжает в фон)

# QAT-native обучение (gemma-4-E2B-it-qat-w4a16-ct)

## Рецепт (изучен и проверен)

1. **Загрузка**: `CompressedTensorsConfig(run_compressed=False)` (новое имя `dequantize=True`) +
   `low_cpu_mem_usage=False` → packed int4 распаковывается в честные `nn.Linear` c bf16
   **QAT-значениями весов**. Никакого bnb сверху.
2. **LoRA-таргеты**: собирать по факту — `type(m).__name__ == "Linear"` + `weight is not None` +
   только текстовый стек (`vision`/`audio`/`multimodal` исключить): 205 модулей
   (q/k/v/o/gate/up/down × 35 слоёв частично — гибридная архитектура).
3. **Гиперпараметры**: те же (r=16 α=32, LR 2e-4 cosine, bs4×accum8, masked CE 262k vocab).
4. **Скорость**: bf16-деквант быстрее bnb-NF4: 0.27 it/s vs 0.21 (40k: ~74 мин vs 199 мин),
   mem 10GB (vs 6.7 NF4 — но на 24GB свободных ок).

## Грабли (обошли)

- `run_compressed=True` (нативно-упакованные слои) — CUDA-only кернелы, на XPU нет
- `Gemma4ClippableLinear` (vision/audio) — peft не умеет; но в текстовом стеке их нет
- слои-«скелеты» без `.weight` при обычной загрузке (веса спрятаны в accelerate-хуках /
  weight_packed) — лечится `low_cpu_mem_usage=False` + dequantize-конфигом
- `quantization_config` нельзя dict при override — только класс `CompressedTensorsConfig`
- `target_modules="all-linear"` падает на кастомных слоях — только явный список таргетов

## CLM (Contrastive-LM 8B) PoC — судья zero-shot

Тест: NF4-XPU энкодер Qwen3-8B + головы CLM, ранжирование gold vs кандидаты.
- **Грубый брак (галлюцинации/инверсии): 4/5 отсечено** — Griggir, Mom's-инверсия,
  possessive «свой/ваш» уверенно детектятся (p до 1.000:0.000). Промах: развёрнутая
  галлюцинация «нава» выиграла у gold (длина/детали соблазнили скорер)
- **Парафразы: 2/4** — CLM ранжирует по поверхностной близости к эталону, валидный
  перевод получает 0.000 против gold. Для Best-of-N без эталона непригоден
- Вердикт: годен как быстрый фильтр грубого брака; точный судья — только после
  fine-tune голов на наших парах (positives 600k + negatives аудита). Приоритет —
  judge-LoRA на малышке (доменный, лёгкий, 2.6B vs 8B-энкодер)
